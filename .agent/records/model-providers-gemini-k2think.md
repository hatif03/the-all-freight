# Drop OpenAI/AI-ML-API for Vertex AI Gemini + K2 Think; local Docker Postgres/Redis

## Context

The planning flow and the ops-room agent swarm both depended on `OPENAI_API_KEY` (directly, or via an AI/ML API gateway acting as an OpenAI-compatible router for six per-role models). The user does not want to use OpenAI API keys anywhere in the project, and wants everything on GCP for convenience (they already have `gcloud` authenticated with a funded Cloud Billing account). They separately provided a K2 Think (MBZUAI/IFM) API key "for reasoning models." They also asked to move local dev off hosted Neon/Upstash onto local Docker Postgres/Redis.

**First attempt (superseded):** the Gemini *Developer* API (`generativelanguage.googleapis.com`), authenticated with a static API key created via `gcloud services api-keys create`. This looked correct — the key and endpoint were verified live — but every real call returned `429 RESOURCE_EXHAUSTED: prepayment credits are depleted`. Investigation found the project's standard Cloud Billing *was* enabled and linked to a funded billing account, but the Gemini Developer API meters against a **separate prepay-credits wallet** (managed at ai.studio) that's independent of that billing account. The user asked "use the AI directly from Vertex?" — which sidesteps that wallet entirely.

## Decision

- **Vertex AI's Gemini models**, via its own OpenAI-compatible endpoint (`https://{LOCATION}-aiplatform.googleapis.com/v1beta1/projects/{PROJECT}/locations/{LOCATION}/endpoints/openapi`, model `google/gemini-2.5-flash` — note the `google/` prefix Vertex requires; `gemini-3.6-flash`, current on the Developer API, 404s on Vertex in this project/region), replace the Developer API everywhere: the planning flow's `src/lib/openai.ts` and four ops-room roles (Logistics, Finance, Procurement, Customer-Impact) via `agents/model_router.py`.
- **Vertex requires an OAuth2 access token, not an API key** (confirmed live: a static key returns `401 ACCESS_TOKEN_TYPE_UNSUPPORTED`). Authenticated with Application Default Credentials — `google-auth` (Python) / `google-auth-library` (Node) — which needs zero credential files: `gcloud auth application-default login` locally (already done on this machine), or the attached service account automatically once deployed on GCP.
- **Tokens expire after ~1 hour.** The agent processes run for days, so the original pattern (build an OpenAI/ChatOpenAI/CrewAI-LLM client once in `main()`, reuse it forever) would start failing an hour into any real run. Every Vertex-routed call site was refactored to fetch a fresh client/token on every LLM invocation instead of at startup: `agents/model_router.py::client_for()` mints/refreshes via `google.auth`; `logistics/main.py`, `finance/main.py`, `customer_impact/main.py`, and `procurement/main.py` all moved their client construction from `main()` into their per-message handler functions. `src/lib/openai.ts` calls `GoogleAuth.getAccessToken()` (which caches/refreshes internally) fresh inside every `jsonCompletion`/`textCompletion` call rather than building one client at module load.
- **K2 Think** (`https://api.k2think.ai/v1`, model `MBZUAI-IFM/K2-Think-v2`) is unchanged from the original decision: a plain static API key, no OAuth, for Carrier and Dissent — the two roles that most need careful reasoning over pattern-matching.
- `AIMLAPI_KEY`, `OPENAI_API_KEY`, and (after the Vertex pivot) `GEMINI_API_KEY` were all removed from `service/backend/config.py`, both `.env`/`.env.example` files, `infra/preflight.py`'s required-key check (replaced with a `GCP_PROJECT_ID` presence check + a live probe through `model_router.client_for()` instead of a static-key probe), `backend/classifier.py`'s dead OpenAI fallback, and every agent's dead "configure OPENAI_API_KEY from AIMLAPI_KEY" startup block.
- Local dev: `service/docker-compose.yml` (Postgres 16 + Redis 7, with healthchecks), `service/.env`'s `DATABASE_URL`/`REDIS_URL` point at the containers by default. `backend/config.py`'s existing defaults already matched this shape — only `.env` needed updating, not the code.

## Consequences

- **Both providers fully verified live, end-to-end, in the running system** — not just curled in isolation. A real (non-injected) simulated disruption ran the complete negotiation: Logistics (Vertex/LangGraph) proposed two genuinely reasoned options citing real alternate ports; Finance (Vertex) costed them and correctly reported "unavailable" rather than fabricating a number with no tariff on file; Procurement (Vertex/CrewAI) and Customer-Impact (Vertex) both contributed; Carrier (K2 Think/PydanticAI) produced a counter-position citing real FMC regulation (46 CFR Part 541); Dissent (K2 Think) raised a material objection; the incident reached `awaiting_approval` with a contested recommendation, and the human approve/reject endpoint closed it out.
- Vertex AI billing is standard Cloud Billing — the same account already funded for other GCP usage, no separate top-up needed.
- The OAuth-token-per-call pattern is a real, permanent complexity increase over a static key: every future Vertex-routed call site must follow it or it will work in a short-lived test and then silently start failing about an hour into a long-running process. Documented prominently in `agents/model_router.py`'s docstring and in `CLAUDE.md`'s "Model providers" section specifically so this isn't reintroduced.
- K2 Think's reasoning depth has a real latency cost worth knowing for demo pacing: Carrier took ~40 seconds on a complex 6-field structured extraction with a long prompt, versus sub-second for simpler K2 Think calls (e.g. Dissent's shorter, more targeted prompt) and sub-second for Vertex/Gemini calls generally.
- Cloud deployment (Postgres/Redis, the FastAPI service, the 7 long-running agent processes, the Next.js app) was intentionally not implemented as part of this — the user wants everything on GCP (frontend on Vercel per a later clarification) but provisioning real infrastructure/billing is a separate decision to make explicitly, not something to do unasked.
